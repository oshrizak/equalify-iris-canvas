# Troubleshooting

Failure modes seen in production, and how to tell them apart. Ordered by
how often they bite and how badly they mislead.

---

## Read the response body before forming a theory

The connector logs Canvas's response body at `WARNING` for every non-404
failure (`connector/canvas/client.py::_raise_for_status`, surfaced on
`CanvasApiError.body`). Look at it first.

A single habit prevents most wasted time here:

**A Canvas error is JSON. An HTML error is your CDN or WAF, not Canvas.**

The status codes are identical, so the body is the only thing that tells
you which layer answered. A 403 that came from CloudFront means the
request never reached Canvas at all — token, scopes, permissions, course
state and page existence are all irrelevant, and every one of them looks
like a plausible culprit if you reason from the status code alone.

---

## `403` with an HTML body — blocked at the edge

**Symptom.** Page writes fail with 403. The body is HTML:

```
<TITLE>ERROR: The request could not be satisfied</TITLE>
<H1>403 ERROR</H1> ... Request blocked. ... Generated by cloudfront
```

Reads succeed. Some documents publish while others never do. Re-consenting,
regenerating keys and changing scopes all fail to help.

**Cause.** Canvas Cloud sits behind CloudFront + AWS WAF. Managed rule sets
inspect the request body and reject anything matching a signature — before
Canvas receives it.

**Confirmed trigger: IPv4 literals.** A bare dotted quad such as
`http://203.0.113.1/tool/` anywhere in the page body — in an `href` *or* in
plain text, over http or https — matches SSRF/malicious-link rules. This is
ordinary course content: plenty of academic tools are hosted at bare IPs.

The connector already handles this. `markdown_to_html._defuse_ip_literals`
rewrites the dots as `&#46;` entities as the final render step. Browsers
decode those in both attribute values and text, so links resolve and the
page reads identically; only the byte pattern changes. Verified against a
production WAF: the raw literal is blocked, the encoded form passes, and
the rule does not decode entities before matching.

**If you hit a different signature.** Bisect the body — it is quick and
conclusive:

1. Confirm the whole body is blocked, then retry with the first half, then
   the first quarter, and so on, until you find the shortest prefix that
   still fails.
2. Print the last few hundred bytes of that prefix. The construct is there.
3. Vary that construct alone — encoded vs raw, linked vs plain text — to
   confirm you have the right one.

Around twenty requests total. Send the offending fragment to whoever
operates the WAF; a one-line reproduction gets a rule exception far faster
than "our integration gets 403s".

**The honest fix** is a WAF exception for the integration. Defusing a
signature in the renderer keeps documents publishing while you wait for
one, but it is a workaround, not a resolution.

## `401` on every Canvas read, shortly after everything worked

**Symptom.** The tool works for about an hour after a user consents, then
every API call returns 401. Re-consenting fixes it — for another hour.

**Cause.** Canvas does not carry consented scopes across a token refresh
when the developer key has **Enforce Scopes** enabled; it substitutes the
key's defaults. A refresh that omits `scope` therefore returns a weaker
token each time, and the tool degrades rather than failing outright.

**Fix.** Already handled: `canvas/user_oauth.py::refresh_user_token` sends
the full `USER_SCOPES` list on the refresh grant, and that list is the same
object the authorize leg uses so the two cannot drift. If your key grants a
narrower set, Canvas answers `invalid_scope` and the connector retries once
without `scope`, logging a warning that names the cause.

Existing tokens minted before this fix stay degraded. Delete the stored
token and re-authorize once:

```
redis-cli DEL "eq-pdf:lti:user-token:<platform_id>:<user_id>"
```

The tool only prompts for consent when no token is stored, so an
already-degraded token must be removed before a launch will re-prompt.

## A converted document never appears in Canvas

Check the review screen first (`/canvas/review`) — it lists every document
the connector knows about and its state.

| State | Meaning | Action |
|---|---|---|
| `Converting` | Iris is working, or the document is waiting its turn | Wait. Iris converts two documents at a time by default, and long documents run as several parts. |
| `Privacy review` | Reflow-era documents only (Reflow Core's PII gate) | Approve or deny in the review screen. Iris documents never stop here. |
| `Ready to review` | Converted, awaiting publication | Read Iris's "Check before approving" notes, then approve to publish. |
| `Page blocked` | Converted; Canvas rejected the page write | See the 403 sections above. |
| `Did not convert` | Iris failed, the file could not be prepared, or Iris went quiet | The row states the reason; the sections below cover each. |

`Page blocked` retries every tick and republishes on its own once the
cause is resolved. No manual replay is needed.

## Startup log: `CRITICAL ... Iris at <url> answers without a token`

**Cause.** Iris's `server.api_token` is blank. Iris has no user accounts,
so an open Iris lets anyone who can reach it list every session
(`GET /v1/sessions`) and read any converted document. On a server that
proxies "everything else" to the port Iris listens on, that is the
internet.

**Fix.** Set `IRIS_API_TOKEN` in Iris's `.env` and the same value in the
connector's, restart both, and make sure Iris is not published through a
reverse proxy. `scripts/preflight.py` re-checks both.

---

## Every conversion fails at once

**Symptom.** Documents go to `Did not convert` within a minute or two,
reading `Iris could not convert this document: ...`.

**Cause.** Almost always Iris's model provider: missing or wrong key,
exhausted credit, a model name the provider does not serve, or a model that
cannot read images. The text after the colon is Iris's own `error`; Iris's
logs carry the provider's response.

**Fix.** Correct the provider settings in Iris, then retry: "Try again" on
the Accessible Documents page for one document, or
`python -m connector.tools.retry_failed_jobs` for every document that
failed meanwhile. Only the parts that failed are sent again.

---

## Nothing converts in a course that used to work

The watcher logs `not converting course <id> until its owner (<user>)
accepts the current disclaimer`. Background conversion acts for the course
owner, and the disclaimer changed with the move to Iris (no PII screening).
The course resumes on its own once that instructor launches the tool and
accepts the new text; nothing needs replaying.

---

## Documents stay in `Converting` for a long time

Iris converts `defaults.max_concurrent_runs` documents at once (2 by
default) and queues the rest; a 25-page part with a review loop takes a few
minutes on a real model. A bulk upload day is a queue, not a fault. Two
things make it slower:

- **Upload pauses.** Iris allows 12 uploads a minute per caller and the
  connector is one caller; `Iris uploads paused for <n>s: 429 ...` in the
  log is the connector waiting as asked. Raise Iris's
  `rate_limits.upload_per_minute` if this is constant.
- **Iris unreachable.** `Iris uploads paused for 60s: unreachable ...`
  repeating means Iris is down; nothing is lost while it is.

A document Iris shows no activity on for an hour is failed by the stale-job
sweeper ("Iris showed no progress on this document ..."). The bridge keeps
checking it and resumes on its own if Iris turns out to be working on it.

## Pictures appear as text: "Image (page N of the original PDF): ..."

Iris reads rasterized pages, so it describes each picture but cannot hand
the picture back. The connector lifts pictures out of the source PDF and
matches them to Iris's descriptions page by page. It shows the description
as text, rather than risk a wrong picture under a right description, when:

- the picture is drawn with vector graphics (most charts exported from
  Excel or PowerPoint) rather than embedded as an image;
- a page has more described pictures than embedded images, or two images
  of similar size for one description;
- the page is a scan (one full-page image).

The bridge log line `figures — X uploaded, Y shown as descriptions` gives
the count per document. Faculty can insert the picture in the page editor;
the description remains correct alt text for it.

---

## A table or sentence is cut at a page boundary like 25/26

Iris converts at most 25 pages per session, so longer documents are
converted in parts and joined. Iris's reviewer reads one part at a time, so
content that crosses a seam is not joined up. The review screen's notes
name each seam ("... converted in 2 parts. Check that anything crossing
pages 25-26 ... reads correctly."); fix the join in the editor before
approving.

---

## Word or PowerPoint files are never converted

The watcher log says `Skipping Word/PowerPoint files: ... LibreOffice
(soffice) is not installed`. Iris reads PDFs only; the connector converts
Office files with LibreOffice first. Rebuild the image without
`--build-arg WITH_LIBREOFFICE=false`, or set
`IRIS_CONVERT_OFFICE_DOCUMENTS=true`. Skipped files are picked up on the
next tick.

---

## Legacy: Reflow-era documents stopped opening after Reflow Core was retired

**Symptom.** Alt formats for a document converted before the switch return
"converted by Equalify Reflow ... not migrated".

**Cause.** The connector used to read those documents from Reflow Core on
every view, and Reflow Core is gone. Iris documents are unaffected.

**Fix.** If Reflow Core can be started again, set `REFLOW_API_BASE_URL`
and `REFLOW_API_KEY`, run
`python -m connector.tools.migrate_reflow_jobs`, then retire it again.
Otherwise use "Try again" on the Accessible Documents page to convert those
files with Iris.
The Canvas Pages themselves were never affected.

## A draft opened from the Files page says to sign in

Unpublished accessible versions open only for an instructor (or TA,
designer, admin) with a live session in that course; the session lasts 8
hours after opening the tool. Open "Accessible Documents" from the course
navigation, then open the link again. (Before, a `?preview=1` link opened
any draft with no session at all.)

---

## The review screen answers 403 "This page belongs to a different course"

The review pages only show the course the LTI session was launched from. A
bookmark or a second tab pointing at another course needs a launch from that
course in Canvas (open "Accessible Documents" from its navigation).

---

## Deleted documents keep reappearing

They shouldn't. The bridge purges a job — record, review-queue entry,
processed marker and page mapping — when Canvas returns 404 for the source
file. Only an explicit 404 purges, so a network blip or an expired token
can never delete a record.

If a row persists for a file that is genuinely gone, the connector is
probably failing to reach Canvas at all. Check the logs for auth errors
rather than deleting Redis keys by hand.
